# R8-2 diagonal pan proposal

This is a scratch proposal against the immutable V21 source at `/tmp/human-ai-v21-final-full-source`. No ROOT file changed. No campaign, performance run, full suite or acceptance re-score ran. Every native diagnostic used CPU 3 and nice 19.

The frozen hands file (`8bd373c3afb8261bf8ca2a53f24512522b91f0ddc6568eaa61dbf7039684b9a3`) chooses one dominant camera-space axis. The actual client combines W/S and A/D in `camera.update`: each component travels `cam.dist * 1.1 * dt` at Normal pan speed, with no diagonal normalization. Client keydown records one physical key; keyup removes that held direction without another input. These are independent useful camera keys, not a compound command or filler.

The candidate prepares the dominant key using the unchanged sampled key motor, presses it, then prepares the other useful direction while the first remains held. Both independently quantized holds move the camera every tick, and each pressed key completes and logs once at its release. A smaller component under one default-camera frame stays cardinal. Distance changes use the actual client `distance * 1.1` rule, not a new authored speed. Map-edge motion applies the native frame displacement before clipping, instead of slowing the entire route to a preclipped endpoint. The commander still waits for the camera job to complete before inspecting the arrival scene.

Each in-flight key reserves an APM slot before starting, so overlap cannot exceed either existing rolling cap. With only one available slot, the first real key finishes and the other waits. An interruption cancels only an unpressed secondary preparation; every already pressed direction completes its full release. Neither an unrelated command nor another selection runs inside the pan job. HUMAN_SKILLS, RNG, reaction floors, opening timing, difficulty limits and economy are unchanged.

`tools/ai-public-alert-response.mjs` adds prospective `panGestureVersion: 2`. New concurrent starts carry `panAxis`, `keyDownTick` and `keyUpTick`. A completed receipt carries `panMotion` with the initial camera, bounds and actual key intervals, including canceled preparations. The sealed native capture remains mandatory. The validator checks real keyboard axes, positive full preparation/hold durations, independent release timing, orthogonal directions and the resulting frame-by-frame end pose. Old cardinal recipes retain the original fixed-target validation path. The policy name, populations, timing endpoints and bands remain unchanged. Historical captures are not rewritten or re-scored.

The test migration deliberately replaces the old L-route behavior assertion. `test-engine-ai-response.js` still requires exactly two useful counted keys, positive motors, no scene planning before completion, fresh arrival deliberation, native selection/command acceptance and genuine emergency causality. It now asserts overlapping key preparation and diagonal motion. The emergency cue is authored after a real key is held; a cue during unpressed preparation would test a different case. Its native held key still finishes at the original tick 96. Arrival completes at ticks 96/99, then the fresh plan at 104 and accepted command at 118. The interrupted cases preserve the immutable screen creation, return camera cost and later accepted retreat.

The alert fixture now expects an uninterrupted diagonal route to reach the marker. Its negative is still real: interrupt before the second key press, finish the first held key, and leave the diagonal marker unseen. New controls preserve both pressed directions through interruption, refuse all starts under an exhausted budget, and reject copied or altered capture intervals. Existing canceled, retargeted, eventless, unrelated-cause, outside-click and unrecorded-state parity controls remain.

The new portable `test-engine-ai-diagonal-pan.js` imports the actual client camera module via a data URL that changes only its Node-incompatible import specifiers. It runs authored native games with ordinary step, viewFor and perceive delivery. It compares every camera frame with the actual client rig, validates actual keys and Three projection, and checks cardinal, diagonal, rotated, reverse, distance 85, sub-frame minor component, cardinal/diagonal clamps, held/unpressed interruption and full/one-slot budgets. Twelve predeclared scenes use seed 27 and eight simulated seconds each. The same scene/seed produces identical traces. These are diagnostics, not acceptance-population fixtures.

`comparison-native.json` retains all frames, paid starts and native input completions for the exact same twelve baseline/prospective scenes and durations. A single queued diagonal trip ends at `(192.4, 100)` on the frozen executor and `(192.4, 162.7)` on the candidate. The candidate pays two keys, starts them at 1000/1002 and releases them at 1030/1023. The shorter direction releases first. It exceeds either intended component by less than one actual simulation frame and then remains stationary. The baseline is intentionally not asserted to equal the client on diagonal or clipped motion: those are the demonstrated defects.

Current focused results are in checks.json. All four pass. The unchanged complete hands suite preserves its existing locality, opening, motor, one-command-per-tick, APM and deterministic gates. No original 180-second child cap is relaxed or removed.

Development failures were inspected rather than attributed to gameplay: the first scratch run failed when copied frozen files were read-only; old response/alert fixtures rejected the intentional new route; the first collector helper incorrectly rejected an orthogonal axis pair; an initial interrupted-key log cleared its stop flag too early; an initial one-slot fixture filled the 10-second cap as well as the 60-second cap; a pending second key canceled one tick too late. The final native intervals, positive-tick budget fixture and immediate unpressed cancellation correct those issues. Failed development runs are not passing evidence. `prospective-native.json` was an intermediate development output and is excluded from the final evidence package; the final paired traces are in comparison-native.json.

Scope limit: this uses the existing fixed viewport, yaw/distance and Normal speed. The default-distance native clamp and distance-85 controls match the actual client rig on these maps. The client's zoomed-out half-wide clamp and alternate speed preference remain outside the existing commander model and this proposal. There is no claim about overall APM improvement, reaction population, win rate or release performance. The two useful direction keys can complete in a different order from their starts; consumers must use their native interval metadata rather than assume the last completion always belongs to the last-started key.
