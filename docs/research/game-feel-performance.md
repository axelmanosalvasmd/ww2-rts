# Three additional runtime improvements

Research date: 2026-10-03. These are proposals, not adopted design decisions or measured improvements. The review read `DESIGN.md`, both October 3 performance reports, `server.js`, `client/gfx.js`, `client/main.js`, `client/stats.js` and `shared/sim.js`, then inspected the additional implementation files cited below. External examples were read from temporary shallow clones, with commits pinned in each link.

The existing work already includes soldier and corpse instancing, distance detail, incremental terrain painting, an opaque paper-map render bypass, cached navigation templates, snapshot deltas and adaptive snapshot frequency. These proposals extend different remaining costs or failure cases. None promises a speedup before a browser or socket workload measures it.

The current evidence leaves room for this work: [the rendering report](../performance-verification-2026-10-03.md#reproduce) explicitly leaves real match FPS and GPU timing unmeasured, and [the World Conquest report](../world-conquest-performance.md#expansion-and-limits) leaves grown-army browser performance, remote networks and extensive reconnect history unmeasured. Healthy bounded server tick results do not settle client responsiveness.

## 1. Spend animation work on the current view

**Player effect:** Panning and selecting a small fight should remain responsive while the rest of a large army moves elsewhere. Returning to an army should show its current posture immediately, without soldiers catching up through several old poses.

**Current local evidence:** `client/main.js:1638-1655` smooths, positions, updates bars, seats trenches and calls `animate` for every client-held unit each frame. `client/unit-models.js:428-449` performs posture blending and visual follower movement before drawing. Existing frustum rejection happens later in `drawSoldiers`, at `client/unit-models.js:498-502`, so it avoids submitting off-screen soldier instances after animation work already happened. This is a CPU interest-management extension, not a proposal to add the existing draw culling or LOD again.

**Specific extension:** Compute conservative camera-interest bounds before expensive visual animation. Continue lightweight center smoothing and snapshot ownership for every held unit. Run detailed follower, pose, bar-facing and trench visual updates at full frequency inside the expanded view. Outside it, age visual state cheaply or update it at a bounded low frequency. On view entry, rebuild the pose from current snapshot state before drawing. Selected units, aircraft entering the view and edge-crossing formations need conservative bounds; never suppress authoritative visibility, incoming-strike warnings or command data because the camera is elsewhere. Measure the linear bound check first; introduce a spatial index only if its maintenance pays for itself.

**Primary implementation:** OpenRA maintains distinct spatial partitions for renderable actors, effects and mouse targets in [ScreenMap.cs:46-76](https://github.com/OpenRA/OpenRA/blob/7d57605bca2cbe963068d42505e00072afe19868/OpenRA.Game/Traits/World/ScreenMap.cs#L46-L76), exposes view-box queries at [lines 193-208](https://github.com/OpenRA/OpenRA/blob/7d57605bca2cbe963068d42505e00072afe19868/OpenRA.Game/Traits/World/ScreenMap.cs#L193-L208), and gathers on-screen actors before renderable generation in [WorldRenderer.cs:259-273](https://github.com/OpenRA/OpenRA/blob/7d57605bca2cbe963068d42505e00072afe19868/OpenRA.Game/Graphics/WorldRenderer.cs#L259-L273). Applying that interest boundary earlier to Three Crossroads animation is an inference, not a claim that OpenRA uses this exact follower policy.

**Acceptance workload and metrics:** Use the grown-army Huge and Massive preview fixture with 64 mobile units per seat. Record three paired ten-minute runs on the same browser, hardware, viewport, DPR and seed, with a scripted camera sequence showing one front, the whole army, rapid pans and paper-map transitions. Report animation CPU p50/p95/p99, whole-frame p95/p99, frames over 50 ms and number of units receiving detailed animation. Adoption requires fewer detailed updates outside the view and a repeatable improvement in frame or animation tails without a regression in the all-visible case. Recording and selection assertions must show no stale posture, popping, lost clicks or changed selection bounds on reentry. Preserve existing corpse expiry and terrain updates.

**Scope:** Medium. The expensive work is already separated, but follower resets, trench seating and click bounds need careful integration.

## 2. Reserve effect capacity for readable combat, with reversible load control

**Player effect:** Heavy shelling can reduce decorative dust and embers while retaining smoke screens, muzzle cues and warning markers. Once pressure passes, decorative detail can return without forcing the player to change the graphics menu.

**Current local evidence:** `client/gfx.js:38-44` switches High to Low after five seconds of slow frames and records a browser-wide automatic-drop flag. `client/perf.js:80-87` assigns a fixed pixel ratio for each graphics level. `client/fx.js:275-276` rejects any new particle at the common cap, while High and Low already have different caps and emission counts. `client/stats.js:16-22` exposes frame, script, draw and scale metrics. Thus the missing feature is priority and reversible load response within a chosen quality level, not another Low preset or another hard particle limit.

**Specific extension:** Give combat-critical visual categories a reserved pool or guaranteed minimum representation. Reduce admission of ambient dust, decorative debris and persistent fire embellishment as ordinary capacity fills. Then use rolling frame-tail measurements to adjust only those cosmetic emission rates within explicit limits, with fast reduction and slow restoration. Keep the saved graphics preference separate from this temporary multiplier. Preserve screen-smoke coverage and warning markers even under maximum load. Do not rebuild terrain or materials as part of this controller. If GPU fill remains the bottleneck after measurement, a separately tested temporary render-scale controller can follow; it is not required for this first slice.

**Primary implementation:** Recoil's [NanoParticleSystem.cpp:438-458](https://github.com/beyond-all-reason/RecoilEngine/blob/10baea878c02c4c18cca42545ae4321a4b959d9c/rts/Rendering/Env/NanoParticles/NanoParticleSystem.cpp#L438-L458) grants high-priority capture/reclaim bursts the full particle budget, limits ordinary spray to a smaller share and progressively rejects ordinary emissions near saturation. [Lines 43-44](https://github.com/beyond-all-reason/RecoilEngine/blob/10baea878c02c4c18cca42545ae4321a4b959d9c/rts/Rendering/Env/NanoParticles/NanoParticleSystem.cpp#L43-L44) set that ordinary share to 0.95. This directly supports reserved capacity and gradual admission. A frame-time feedback controller is the proposed local extension; that source does not establish one.

**Acceptance workload and metrics:** Replay the same seeded artillery, aircraft crash, screen-smoke and burning-town sequence on High and Low, with ordinary particle load below, near and above current caps. Include a quiet recovery minute and a background-tab return. Measure frame p95/p99, frames over 50 ms, particle admissions/rejections by priority and controller changes per minute. Require zero dropped warning markers, a visible smoke-screen footprint at saturation, stable bounded counts, unchanged server damage/visibility and no graphics-setting writes by the temporary controller. Require repeatable frame-tail improvement in the overloaded case before claiming performance benefit; reject distracting quality oscillation or a quiet-view regression. Include video proof of overload and restoration.

**Scope:** Medium. A fixed priority reserve alone is Small; category-aware admission and a stable reversible controller require more integration.

## 3. Verify replicated content, then recover it atomically

**Player effect:** A corrupted or stale row should not leave a tank at the wrong position or health until it next changes or the player reloads. The client should recover the affected view and make recovery visible in diagnostics.

**Current local evidence:** `shared/sim.js:3907-3919` sends a count and xor of unit IDs. `client/main.js:753-764` checks those IDs and requests a full resend on mismatch. The mechanism already recovers missing/extra IDs. It cannot detect changed health, position or flags when the same IDs remain, and different equal-sized ID sets can share the same xor. `server.js:453-456` already supports a full resend, and `server.js:162-179` retains wreck/node versions separately. This is an extension of that recovery contract, not a proposal to introduce resync again. It addresses application drift, not alleged TCP packet loss.

**Specific extension:** Add a protocol version, match epoch and stable checksum of canonical client-visible unit rows, plus explicit versions/checksums for retained lists. Compare checksums only after the complete snapshot transaction is applied. On mismatch request a versioned full replacement using the existing resend path, validate it into temporary collections and swap them together. Use periodic content checks if hashing every snapshot costs too much. Show last recovery tick, mismatch category and recovery duration in diagnostics. Hash only the receiving seat's authorized, rounded view; global authoritative hashes would disclose or compare hidden information incorrectly. Full-state recovery must account for the retained lists included in the checksum. Terrain/fog checkpoints can be a later, separately scoped extension.

**Primary implementation:** OpenRA computes content-based state hashes over actors, synchronized traits and relevant effects in [World.cs:482-500](https://github.com/OpenRA/OpenRA/blob/7d57605bca2cbe963068d42505e00072afe19868/OpenRA.Game/World.cs#L482-L500) and compares hashes by frame in [OrderManager.cs:161-169](https://github.com/OpenRA/OpenRA/blob/7d57605bca2cbe963068d42505e00072afe19868/OpenRA.Game/Network/OrderManager.cs#L161-L169). Its deterministic lockstep mismatch detection is the reference for checking content. Three Crossroads' authoritative filtered snapshots permit replacement recovery; automatic atomic replacement is our proposed adaptation, not behavior claimed for OpenRA.

**Acceptance workload and metrics:** In a real-socket six-seat Massive match, inject a wrong position and health value without changing IDs, an equal-count/equal-xor ID substitution, a stale retained list, a duplicate snapshot and an old-match snapshot after restart. Test players and the shared spectator stream. Require detection at the next scheduled content check, at most one outstanding recovery, recovery within two normal snapshot intervals on an unstalled connection, exact filtered-state agreement after replacement and zero hidden-data additions. Also run 100 reconnect/restart cycles and a 30-minute healthy session with zero false recoveries. Report checksum CPU p95, bytes added per snapshot, mismatch count and recovery latency. Hashing must leave the existing 50 ms server budget intact on the same controlled fixture; do not claim a speed improvement from this reliability feature.

**Scope:** Medium for unit rows and retained lists. Including full terrain/fog checkpoint recovery would make it Large.

## Suggested order

Measure and prototype the view-aware animation boundary first. Its current cost is directly visible in the frame loop and the existing draw culling gives a conservative starting point. Next, reserve effect capacity so overload preserves useful combat cues. Content-verified recovery is the strongest reliability candidate, especially before stronger transport coalescing or camera-based network interest is attempted. Camera-based network interest is intentionally deferred: the current fog-filtered stream also serves minimap and off-screen orders, and its deltas cannot simply be dropped without repairing the receiver baseline.
